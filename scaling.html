FPGA array vs CPU — scaling outlook

Where a mesh-of-RISC-V-cores simulator beats a CPU, as a function of design size. Solid dots and solid lines are measured runs with checked outputs; dashed lines are speculation or hypothetical and are labelled as such. Updated 2026-11-20 with the first runs on AWS F2 silicon.

What was measured

The benchmark is a torus of SHA-256 round cells (“SHA-mesh”): every cell does one SHA-256 round per clock and mixes in the state of its north and west neighbours, so all traffic is local. One cell synthesizes to about 7.7k gates (yosys, generic two-input gates plus 1,062 flops, inverters not counted). Each array node is a RISC-V core with a wide-word engine beside it: a 128-bit, four-lane datapath with its own 4096-word memory that runs a straight-line microprogram and evaluates four neighbouring cells at once. A node holds 64 cells.

All three FPGA arrays reproduce the reference model’s signature over every cell at 64, 200, 256 and 2,000,000 clocks. The x86 host is a 16-core Threadripper PRO 5955WX; Verilator was built at 1, 4, 8 and 16 threads for each size and the best is plotted (4 threads at 20×20, 8 from 24×24 to 56×56, 16 at 80×80). The F2 run matches the cycle-accurate simulation of the array to five digits.

How to read it

A CPU simulator slows down as the design grows: more gates to evaluate per clock, and past a few million gates the state no longer fits in cache, so extra threads stop helping. The measured Verilator curves show both effects: 209k clocks/s at 3M gates, 12k at 49M.

The engine array is flat. One simulated clock costs 219 FPGA clocks whatever the array size, because every node works on its own 64 cells in parallel and only exchanges edge values with its neighbours. So the three arrays, with 9, 12 and 49 nodes, run at the same rate within 4%, and the advantage over Verilator grows with size until the device is full: 5.3× at 5.9M gates and 19× at 24M gates. Below about 1M gates Verilator on a desktop is as fast or faster.

The engine matters more than the core count. The same 49 nodes using only the RISC core and a SHA logic extension reach 25.6k clocks/s, slightly below Verilator. The wide-word engine is 22× faster than that for about 14k LUTs and 17 block RAMs per node.

Limits of these numbers

  • The test case is cherry-picked. SHA-mesh is a regular 32-bit datapath with only nearest-neighbour traffic, which is the best case for a four-lane word engine and a mesh. Control-heavy or bit-level logic will map less well.
  • The microprogram comes from a scheduler script written for this cell. Nothing yet compiles arbitrary RTL onto the engine, so these are hardware-capability numbers, not tool-flow numbers.
  • The 12-node ZCU104 array uses 83% of the device’s LUTs and met timing at 125 MHz, so that board is close to full.
  • Capacity is set by state, not gates: a node’s memory holds 64 cells of about 1,000 state bits each. A design with more state per gate fills the array sooner.

There is no wide-word engine, so it sits where our RISC-only runs would with many more cores.

What would move these lines: a second, less regular test case on the engine; a compiler from RTL to the engine microprogram; and a Verilator run on a larger server.
